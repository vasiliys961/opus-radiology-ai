## Какие настоящие блокировки обнаружил тест

1. **Не распознавались допустимые HU при отсутствии Rescale Type.** У файлов
   есть classic CT Image Storage, ORIGINAL/AXIAL, корректные slope/intercept,
   нет Multi-energy YES. По [DICOM PS3.3 C.8.2](https://dicom.nema.org/medical/dicom/2025d/output/chtml/part03/sect_C.8.2.html)
   для этих условий выходная шкала HU; отдельный тег необязателен. Исправлены
   оба парсера. Модальность сама по себе, одни коэффициенты, DERIVED, LOCALIZER,
   неизвестный SOP Class и multi-energy без явного HU не дают такого разрешения.
   Неверные/отсутствующие численные коэффициенты по-прежнему блокируются.
2. **Четыре полноразмерные парные копии превышали HTTP/base64-ограничения.**
   Реальный сервер вернул 413 до инференса. После проверки копии перегруппируются
   по фактическому размеру: пиксели, PNG SHA, исходные номера и решения проверки
   не меняются. Аналогично собираются пакеты визуального Opus. Размеры тела,
   PNG, число 16 и четыре пакета Opus не повышались. Если в четыре пакета входят
   не все отмеченные кадры, охват содержит только действительно включённые.

Предшествующие неуспешные попытки были до модельного инференса: отказ локальной
подготовки HU, EOF неинтерактивного тестового подтверждения и HTTP 413. Первый
диагностический скрипт ожидал скрытую ошибку подготовки до таймаута; теперь
причина считывается сразу. Для ручной проверки точных PNG требуется TTY.
