# Сравнение Doctor Opus Global и локального радиологического модуля

Дата: 02.11.2026. Кодовый аудит, без новых модельных вызовов, передачи исследований или проверки диагностической точности.

Проверены:

- Текущий локальный `opus-radiology-ai`, `bf2a8a8`, включая изменения рабочего пути врача.
- В родительском проекте прослежены `components/ImageUpload.tsx` → `lib/dicom-client-processor.ts` → `app/image-analysis/page.tsx` → `/api/analyze/image` → `lib/openrouter-streaming.ts`/`lib/openrouter.ts`. Общий диагностический консилиум рассмотрен отдельно; не считается автоматически работающим для каждой DICOM-загрузки.

## Вывод

Само сочетание Gemini → Opus уже есть в родительском проекте. Нынешний локальный маршрут на четырёх кадрах не даёт оснований утверждать более высокую диагностическую точность. Его полезное отличие — проверяемая связь с исходными DICOM, геометрия, локальная работа с изображениями и возможность присоединять настоящие измерения/модельные результаты. Это основа для усиления, а не доказательство превосходства.

## Что найдено в родительском проекте

1. **Папка не означает просмотр всего исследования.** `sliceDicomFolder(files, maxFrames=12)` равномерно выбирает индексы входного списка. В найденной функции нет группировки по SeriesInstanceUID и сортировки по физической координате; вызывающий `ImageUpload` передаёт отфильтрованный список. Двенадцать — предел выборки в этом пути, а не предел всего API или всех функций проекта.
2. **Opus может видеть изображения.** Потоковый `analyzeMultipleImagesOpusTwoStageStreaming` передаёт второму этапу JSON Gemini и `imagesBase64`. Поэтому добавление изображений Opus само по себе не новая возможность нашего модуля. При этом непотоковый одноизображенческий `analyzeImageOpusTwoStage` передаёт второму этапу только текст; пути различаются.
3. **Клинический вопрос и контекст.** Основная страница передаёт `clinicalContext`, результаты лаборатории и опциональный библиотечный контекст. При работе непосредственно с DICOM сервер добавляет некоторые метаданные. При предварительном преобразовании папки в JPEG исходные теги не проходят этим же серверным DICOM-путём.
4. **Более богатое визуальное описание.** `getDescriptionPrompt` включает качество, артефакты, локализацию, морфологию, измерения, важные визуальные отрицательные признаки, критические признаки и неопределённость. Это запрос к модели, не доказательство достоверности её измерений или самооценки уверенности.
5. **Повторная оценка предусмотрена, но не гарантирует усиления.** Smart routing может учитывать сложность/качество. В текущих константах `GEMINI_3_PRO` и `GEMINI_3_FLASH` указывают на одну `google/gemini-3.8-flash`; код отдельно проверяет наличие отличающейся Pro-модели. Нельзя считать такой псевдоним независимым более сильным чтением.
6. **Общий консилиум не равен объёмному анализу.** `lib/diagnostics/orchestrator.ts` содержит профильные мнения, скептика и согласование. Увеличение числа текстовых ролей не возвращает пропущенные срезы и не доказывает независимое визуальное подтверждение.
7. **Возможное дублирование первого изображения.** Для папки `ImageUpload` вызывает `onUpload(slices[0], slices, dicomFiles)`, страница сохраняет все `slices` в additionalFiles и отправляет основной файл плюс дополнительные. Сервер собирает `[file, ...additionalImages]` без дедупликации в этом участке. Требуется воспроизведение, чтобы подтвердить эффект в развёрнутом интерфейсе.
8. **Подготовка изображения может менять видимость.** Выборка рендерится в offscreen-области 512×512 в JPEG quality 0.85, проверяется по средней яркости/вариативности; сервер дополнительно выполняет обработку и возможное скрытие областей. Эти операции требуют проверки диагностической сохранности, а не предположения о пользе «улучшения изображения».

## Что найдено у нас

| Участок | Фактическое поведение | Ограничение для диагностической задачи |
|---|---|---|
| Обычный врачебный путь | `MAX_VISION_SAMPLE_FRAMES=4`, одна выбранная геометрически проверенная серия | Патология между кадрами может не попасть в запрос вообще |
| Gemini | `reviewMessages`: модальность, синтетические ID, пиксели; «Review each independently» | Не передаются полноценный протокол и клинический вопрос; не задано прослеживание очага между соседними срезами |
| Наблюдения | ID кадра, anatomy, sign, uncertainty; до 8 кратких находок, 1800 токенов ответа | Мало структуры для морфологии, стороны, диапазона срезов и проверяемого измерения |
| Opus в четырёхкадровом пути | Те же изображения, JSON Gemini, выполненные detector facts, до 3500 токенов | Видит лишь выборку; JSON Gemini уже известен во время чтения, поэтому это не слепое независимое чтение |
| Связь с источником | SOP/геометрия остаются локально; проверяются точные кадры и хеши | Ссылка на кадр ещё не является точной границей очага или верным размером |
| Полный проход | Есть `prepareOriginalVolumeBatches`, ledger, receipts, Gemini batches, финальный Opus | Включён отдельным исследовательским путём, не заменяет обычные четыре кадра и не принят на 267 срезах |
| Декодирование полного прохода | По умолчанию старый `decodeDicomPreview` | Исправление сжатых DICOM для обычного пути ещё не перенесено сюда |
| Приватность полного прохода | Использует auto OCR/redaction для отдельно разрешённого публичного режима | Нельзя просто включить его для любого исследования; ложное OCR-скрытие анатомии уже было проблемой обычного пути |
| Повторный проход | flaggedIndices задаются до начала; в UI — выбранный индекс | Нет автоматической очереди новых подозрительных очагов по результатам первого прохода |
| Итог полного прохода | Opus получает только текст Gemini и detector facts | Для спорного очага нужна отдельная визуальная проверка, иначе визуальная ошибка Gemini может сохраниться |
| Вместимость и бюджет | До 180 наблюдений для одного финального запроса; Gemini budget в компоненте $0.50 | Длинный/многопатологический ряд может завершиться отказом по размеру или бюджету. Нужна управляемая агрегация, а не молчаливое отбрасывание |
| КТ-окна и МР-серии | Просмотр и отдельные проверки протокола существуют | Текущий облачный запрос не является системным многоконным или многопоследовательностным исследованием |

## Что усилит модуль: порядок реализации

### 1. Довести просмотр выбранной серии целиком

Использовать существующий потоковый механизм пакетов, не писать ещё один оркестратор. Добавить проверенный декодер, безопасную подготовку кадров, явное разрешение точного объёма и расходов. Сохранять физический порядок, не смешивать серии. Показывать обработано N/M и ошибки конкретных кадров. При остановке сохранять частичный результат с точным охватом; не называть неполный ряд полным анализом.

Приёмка: 267 исходных кадров, каждый имеет подтверждённую запись обработки либо явную ошибку; ни один не пропущен молча; есть отмена и фактический расход. Это технический охват, не доказательство диагностической полноты.

### 2. Дать модели протокол и пространственный контекст

Для каждого кадра передавать разрешённые технические сведения: псевдоним серии, физический порядок/позицию, шаг и ориентацию, применённое окно. Область, фаза и МР-последовательность — только по подтверждённым данным либо «не определено». Добавить необязательный структурированный клинический вопрос без идентификаторов; не отправлять произвольные DICOM descriptions или всю историю автоматически.

Видимые окна КТ выбирать по задаче; дополнительные окна и ограниченные исходные MPR-фрагменты должны иметь отдельную привязку к источнику и учитываться в расходах. Для МРТ сопоставлять доступные серии одного исследования и явно показывать отсутствующие последовательности. Не решать проблему RAM увеличением нынешних guards.

### 3. Повторно просматривать очаг, а не повторять весь отчёт

Gemini возвращает структурированную находку: ID, кадры-доказательства, анатомия/сторона, морфология, неопределённость и запрос на проверку. Система формирует ограниченный набор соседних срезов и нужных представлений. Повторные наблюдения одного очага объединяются в одну запись с сохранением всех исходных доказательств.

Для спорных/значимых очагов Opus сначала получает изображения без диагноза Gemini, затем сопоставляет независимую запись с его результатом. Результат модели и её confidence не считать вероятностью диагноза. Физические размеры/HU считать кодом из исходной геометрии и выбранной ROI, а не принимать выдуманные числа из PNG.

Приёмка: один очаг на нескольких срезах не превращается в несколько опухолей; каждая ссылка открывает нужный оригинал; разногласие остаётся видимым. Если визуальная проверка не выполнена, итог не утверждает обратного.

### 4. Сопоставить на одинаковых размеченных случаях

Родительский текущий путь, наш текущий четырёхкадровый путь и улучшенный полный путь получают одни исходные исследования и одинаковый клинический вопрос. Фиксировать версии моделей, параметры, бюджет, реальные переданные кадры/окна, ошибки подготовки и идентификаторы запусков. Проверять экспертно подтверждённые положительные и отрицательные случаи, пропуски, ложные находки, сторону, локализацию, измерения, время проверки врачом и стоимость. Согласие Gemini/Opus, самооценка модели, зелёные тесты и красивый протокол не являются метрикой диагностического превосходства.

## Что переносить и чего не делать

Переносить из родительского проекта: полезные протокольные checklist, оценку качества/неопределённости, клинический вопрос, возможность независимого визуального второго чтения. Адаптировать их к нашей схеме источников и авторизации, не копировать весь универсальный промпт.

Не начинать с новых моделей, десятков «ролей врачей», длинного профессорского промпта или повышения лимита с 4 до 267 в одном запросе. Не снимать приватность, ресурсные ограничения и лимит расходов ради зелёного статуса. Не обещать превосходство до сравнительных измерений.
